# CMMS v1.2 — Production readiness plan
Status: IN DEVELOPMENT. Branch: `develop/v1.2-rbac-production-readiness`. Do not merge into main or use on live data until gates pass.

## Collaboration contract
- Product owner: defines real user workflows, validates acceptance criteria and signs off.
- Development: designs secure implementation, writes tests, maintains evidence, changelog and documentation.
- Every change: requirement ID → implementation → automated tests → manual user acceptance → documentation → release decision.
- No test is marked PASS without a recorded command/result and version/commit. NOT RUN is not PASS.
- Do not replace production data with demo data. Demo data is isolated, repeatable and explicitly labelled.
- Preserve existing users, password hashes, permissions, and accounting records through migrations.

## Role matrix (planned; server enforcement required)
| Role | Work orders | Purchase orders | PM | People | Finance | Reports | Users |
|---|---|---|---|---|---|---|---|
| Administrator | All | All | All | All | All | All | All |
| Manager | Create/manage | Create/request/manager approve (separation of duties) | View | View | No posting | Operational | No |
| Supervisor | Assign/monitor | Supervisor approve (separation of duties) | View | View | No posting | Operational | No |
| Coordinator | View | None | Create/edit | Update technician details | None | Operational | No role/password changes |
| Finance Admin | View relevant references | Finance-related view | None | None | All financial transactions | Financial | No |
| Technician | Own assigned WO progress only | None | Own assigned PM WO | Own profile view | None | Own WO/completion reports | None |

Notes: Manager, Supervisor, Coordinator and Finance Admin are specialist roles, not a blanket inheritance chain. Approval segregation, record ownership, and API-level authorization override UI navigation. Technician access must filter both state and report responses server-side. Self-report PDF must contain only own records.

## Delivery gates
1. **Baseline**: inventory modules/routes; existing test suite passes; snapshot/rollback documented.
2. **RBAC foundation**: role policy, schema migration, login/session role handling, account administration, permission tests.
3. **Server enforcement**: each state mutation and finance/procurement/report/file route protected; ownership and approval separation verified.
4. **UI**: role-specific navigation, technician self-service and printable own reports.
5. **Demo dataset**: extend existing `demoState()` fixture, deterministic where possible; seed only isolated test DB; cover all modules and role personas.
6. **Systematic test runner**: unit, integration, API authz, workflows, reporting, backup/restore, regression and negative tests; repeatable machine-readable results.
7. **UAT**: user executes scripted scenarios, records PASS/FAIL with screenshots or notes.
8. **Release**: migration dry run, security review, backup/restore, release notes, approval, tagged v1.2.

## Immediate known risks
- Existing schema restricts role to ENUM('admin','technician').
- Current state GET exposes broad operational data to technicians.
- Current state PUT only distinguishes administrator versus technician.
- Finance endpoints use administrator-only checks; need role-specific authorization.
- Existing demoState() covers operational modules but not SQL accounting/role personas.
- The role model must not be activated until all endpoints have been audited.

## Update discipline
Update `docs/TEST_PROGRESS.md` and `docs/CODE_EXPLAINED.md` with each accepted change. Mark tests unverified until executed in the target environment.
